### 可采纳的工程经验（已与代码/官方文档交叉核对）

1. **不要把探针 RTT、WireGuard 握手耗时和数据面可用性混为一谈。**
   - 卡卡 `NativeCore.handshakeGate()` 的引擎返回格式是 `ip:port<TAB>握手耗时ms`，Kotlin 按握手耗时升序解析，但当前只保留地址、丢弃每节点耗时。
   - `probeLive()` 日志里的“最快”是 UDP 存活探针最快，不等于 WireGuard 握手最快，也不等于真实吞吐最快。
   - 因此，07:40 日志中 `8.39.214.6:500` 是最快 UDP 探针、最终候选首位却是 `8.47.69.103:1701`，**不能据此判定候选排序错误**。此前把两种 RTT 直接比较的诊断应更正。
2. **握手成功不等于可上网。** 卡卡已有 TCP 数据面探测和后续 OpenAI DNS/TLS/HTTP 诊断；XEHN 的 `health.go` 也明确把“真实请求通过代理完成”作为 connected 的判据，握手/监听端口只是前置条件。对卡卡应继续保留“隧道可用”与“特定网站 HTTP 被拒绝”两层结论，不把 401/403 当作隧道坏节点。
3. **节点 UI 要显示真实测量值。** XEHN Windows Nodes 源码有搜索、可用/收藏筛选、延迟排序、当前/已选状态；Home 源码对上传/下载无采样时显示“等待数据”，不伪造 0 B/s。可借鉴信息层级，不移植 Windows UI/核心实现。
4. **Cloudflare 接入端点不等于独立出口地区。** Cloudflare WARP FAQ 指出最近的边缘不一定是实际连接点，路由、运营商路径和边缘健康都会影响选择。节点选择应依据真实握手、数据面与稳定性；不能把 IP/端口切换承诺成换国家或解除网站限制。
5. **移动网络变化需要单独观测。** Android 官方 `ConnectivityManager.NetworkCallback` 提供 `onAvailable/onLost/onCapabilitiesChanged` 等事件。当前卡卡 `TherVpnService` 未注册 NetworkCallback，`NetInfo` 只读取当前网络快照；后续可评估在移动数据/Wi-Fi 切换时记录网络变化并触发有界恢复。
6. Android 官方文档确认 `VpnService.Builder.excludeRoute(IpPrefix)` 从 API 33 提供；卡卡原生核心使用该能力排除 WireGuard 对端路由。用户设备 Android 17，高于该 API 要求；本次日志不能把 API 版本当成当前故障原因。

## 卡卡当前代码审查

- Home 已显示连接阶段、出口/本机 IP、国家地区、周期 RTT 和当前连接消息。
- Home 当前没有实时上下行速率卡、会话计时或丢包指标；不能用握手耗时替代这些指标。
- NodeScreen 目前只读最近 15 分钟的持久化真握手缓存，行内只有 IP/UDP 端口和“最近握手验证通过”，没有每节点 RTT/丢包/数据面状态；缓存为空时提示“先回到首页连接一次”。因此首次连接前打开节点页，确实没有可选节点；如果连接最终失败并清掉缓存，也可能没有可选项。当前没有独立的“立即扫描/刷新”按钮。
- 后续节点页改进优先级：明确扫描状态与刷新入口；保存并展示每节点真实握手耗时；将“握手通过”和“数据面通过”分开标记；丢包只有实际测量后才能显示。不要虚构质量百分比。
- 后续 Home 改进：真实上下行计数/采样曲线、会话时长、阶段耗时；无采样时显示“等待数据”。网络变化事件与健康检查应分开记录。
- XEHN 是 Windows + mihomo 项目；其代理模式、TUN、系统代理、端点扫描和数据面实现与 Android `VpnService + wireguard-go` 不同，不能直接照搬 Windows 端协议切换或管理员权限逻辑。
